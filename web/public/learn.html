A payment system is the standard interview question for exactly-once semantics in a distributed system, because money makes every failure mode expensive. This page is the design behind the playground: what it must guarantee, how each guarantee is bought, and what it costs.

01 The problem

Taking a payment means coordinating three systems that can each fail independently: your database, a message broker, and a payment provider you do not control. None of them can participate in a shared transaction.

Every hard question in this design comes from one fact:

The fact everything follows from When a network call times out, you cannot tell whether it succeeded. The request may have arrived and been processed, or never arrived at all. Both look identical to the caller.

If you could tell, you would simply retry when it failed. You cannot, so the system has to be built so that retrying is always safe.

02 Requirements

Functional

  • Accept a payment request
  • Submit the charge to a provider
  • Track it to a terminal state
  • Accept provider callbacks
  • Let operators see what happened

Non-functional — the real question

  • Never charge twice, under any retry
  • Never lose a payment, under any crash
  • Survive provider downtime
  • Survive our own process dying mid-flight
  • Every state change auditable
Scope taken here IDR only, treated as zero-decimal. One merchant. Single Kafka partition. No refunds, partial captures or 3DS. Those are deliberate cuts, not oversights — each is called out where it would change the design.

04 The core problem: dual writes

Creating a payment means doing two things: writing a row, and telling the rest of the system about it. They live in different systems, so they cannot be one transaction. There are only three options, and two of them are wrong.

You cannot make two systems atomic. You can avoid needing to.
Say this in an interview The outbox does not make delivery reliable — it makes the database the single source of truth and lets delivery be unreliable. The relay can publish the same event five times; consumers deduplicate. What it can never do is lose one.

This was not theoretical here. A disk-full incident mid-project destroyed every Kafka message and every consumer offset. Not one payment was lost, because Postgres held the truth and the relay replayed from the outbox.

05 The state machine

Two terminal states. Everything else is a waiting room.
Why UNKNOWN is its own state After a timeout, leaving a payment at PENDING is a lie. PENDING means "not submitted", and anything reading it — a human, a retry job, a dashboard — will conclude a charge is safe. It is not. The money may already have moved. UNKNOWN makes the dangerous case loud instead of hiding it inside a status that looks fine.

Terminal states are also the ordering rule. Every settlement goes through one guard: 

UPDATE payments SET status = $2
WHERE id = $1 AND status NOT IN ('SUCCEEDED','FAILED')

The webhook and the reconciler can both try to settle the same payment at the same instant. Whichever commits first wins; the loser's UPDATE matches zero rows and it stands down. No locks, no coordination, no leader election — and no version numbers needed, because with one hop and two terminal states, "never leave a terminal state" is the whole rule.

06 Four layers of idempotency

People answer "use an idempotency key" and stop. That covers one of four places a retry can duplicate work. Each layer protects a different boundary.

#BoundaryMechanismStops
1Client → APIidempotency_keys.key PRIMARY KEY + ON CONFLICT DO NOTHINGa network retry creating two payments
2Worker → gatewayIdempotency-Key: <payment id>a retried charge taking money twice
3Kafka → workerprocessed_events (consumer, event_id)a redelivered event being applied twice
4Any status writecompare-and-set in the WHERE clausea stale writer reopening a settled payment
The line that matters Postgres enforces idempotency, not application code. Check-then-insert races: two concurrent requests both find nothing and both insert. Putting the key in a unique index makes the database pick the winner. Tested with 30 parallel requests on one key — 1× 201, 29× 200, one row.

Exactly-once does not exist. Exactly-once effect does.

Every hop here is at-least-once: the relay can publish twice, Kafka can redeliver, the worker can retry. What the four layers buy is that doing any of it twice has the same result as doing it once. That distinction is the single best thing to say when someone asks about exactly-once delivery — claiming you achieved it end to end is a red flag.

The two rows people miss Timeout is never retried inline. Retrying is safe from a double-charge standpoint — the key sees to that — but the first request may still be executing, a provider that is timing out is already overloaded, and a retry will almost certainly time out too. You burn another full timeout to learn nothing.

"No record" is never acted on. "That charge never existed" and "I lost my records" look identical over HTTP. Acting on the second one either loses a real payment or charges someone twice. A human decides.

Order of operations in the worker

Call the gateway before writing anything. The asymmetry decides it:

It also keeps a database transaction from staying open across an HTTP call, which is how you exhaust a connection pool the first time the provider gets slow.

On money and floats BIGINT in whole rupiah, never a float: 0.10 has no exact binary representation. And INT is a bug here, not a limit — it overflows at about Rp 2,1 miliar, which is a normal property or B2B transfer. In USD the same mistake hides until production, because INT holds $21M in cents.

The partition trap hash(key) % 3 and hash(key) % 6 give different answers. Adding partitions to a topic that depends on key ordering breaks it permanently — existing keys remap, and no replay fixes it. Over-provision at creation, or move ordering into the data with version numbers so the topic layout stops mattering.

10 Interview answers

How do you stop double charges?
Four layers, not one. The client's key is a unique index so Postgres picks the winner under concurrency. The worker sends the payment id as the gateway's idempotency key, so a retried charge replays the first one. Consumed events are deduplicated in an inbox table written in the same transaction as their effects. And every status write is a compare-and-set, so a stale writer cannot reopen a settled payment.
Can you guarantee exactly-once?
Not delivery — nobody can across systems. Exactly-once effect, yes. Every hop is at-least-once and every operation is idempotent, so doing it twice equals doing it once.
The gateway times out. What now?
The charge may or may not have happened, so the payment goes to UNKNOWN — never back to PENDING, which would claim nothing happened. It is not retried inline: the first request may still be executing, and a provider that is timing out is already overloaded. Reconciliation asks the gateway later, once it has recovered.
The webhook never arrives.
That is why reconciliation exists. Every other path is event-driven, and event-driven systems lose events. The reconciler depends on nothing being delivered: it polls our own database for payments stuck past a threshold and asks the provider directly, because the provider is the authority on whether money moved.
Two webhooks arrive out of order.
Terminal states are the ordering rule. Settlement is guarded by WHERE status NOT IN ('SUCCEEDED','FAILED'), so the first terminal answer wins and anything later matches zero rows. For a longer lifecycle I would put a version number on each event and track the last applied version, which survives repartitioning and multiple topics.
How do you keep events ordered in Kafka?
Ordering exists only within one partition of one topic, so the partition key is the aggregate id — the payment id. That gives ordering per payment and parallelism across payments. The catch people miss: if your events live in separate topics per event type, there is no ordering between them no matter what the key is.
Why not just publish to Kafka directly?
A database commit and a publish are two systems with no shared transaction. Publish-then-commit announces payments that do not exist; commit-then-publish loses payments silently. The outbox makes both writes one transaction and lets a relay handle delivery, which is allowed to be unreliable because consumers deduplicate.
What would you add next?
Retention on the three append-only tables; leader election for the relay once there is more than one replica; a dead-letter drain; per-currency exponents if this stopped being IDR-only; and real observability — the counts by status are the business metric, and a rising UNKNOWN count is the page-someone signal.
If you remember one thing You cannot tell a timeout from a failure. Every mechanism here — the outbox, the idempotency keys, the inbox, UNKNOWN, the reconciler — exists to make that ambiguity survivable rather than to pretend it away.
